The authoritative working project is `/home/shiki/Documents/github/Kartikaris`; `/home/shiki/Documents/github/Katarsis` remains a read-only historical donor/reference, `/home/shiki/Documents/github/Ritual Division` is the read-only heading-display donor, and `/home/shiki/Documents/github/FireForEffect` is a read-only presentation and synthesized-audio reference.

## Implemented Systems

### Procedural terrain

`Assets/Scripts/WorldGeneration/KartikarisTerrainGenerator.cs` writes deterministic layered Perlin-noise heights into the assigned existing TerrainData. It exposes Generate Terrain, Regenerate Current Seed, and Flatten Terrain context commands, preserves configured TerrainData dimensions/resolutions during generation, and does not change global `UnityEngine.Random` state.

Current/default settings are seed `12345`, base elevation `30 m`, amplitude `24 m`, primary noise scale `300 m`, four octaves, persistence `0.4`, and lacunarity `2.0`.

The fresh TerrainData is configured as `1024 × 120 × 1024 m`, heightmap resolution `513`, detail resolution `512` with `32` per patch, control texture resolution `512`, and base texture resolution `1024`.

### Dense forest

`Assets/Scripts/WorldGeneration/KartikarisForestGenerator.cs` creates deterministic Unity `TreePrototype` and `TreeInstance` data. It does not create a GameObject per standing tree. It performs bounded placement with terrain-edge, slope, density, and minimum-spacing rejection; spacing uses a lightweight spatial grid.

Current/default settings are seed `67890`, target `25,000`, minimum spacing `3 m`, maximum slope `35°`, scale `0.85–1.2`, edge margin `15 m`, density scale `180 m`, density strength `0.25`, and twelve attempts per requested tree. The hard development ceiling is `250,000` trees. Context commands generate/regenerate and clear the forest.

The scene contains 25,000 authored Terrain tree instances using ten valid Synty prototypes from the fresh import. Forest generation does not alter the heightmap.

### Simulated tracked / roller-foot controls

`Assets/Scripts/Player/TrackedDriveModel.cs` is a small pure helper shared by Player and Enemy. From analog-friendly throttle/steering input plus actual longitudinal speed, it returns virtual left/right roller commands, stationary-pivot state, longitudinal speed multiplier, and tuned yaw rate. It does not simulate contact forces, drivetrain torque, suspension, wheel colliders, or Rigidbody physics.

`Assets/Scripts/Player/MechFirstPersonController.cs` retains its filename/component identity, Input System bindings, CharacterController authority, gravity, acceleration/deceleration, and tree-crusher path. While fully in Travel, W/S remain signed throttle along `Player.transform.forward`; there is no strafing and physical movement never uses camera direction. Current tuning is forward speed `6 m/s`, reverse speed `5 m/s`, acceleration `12 m/s²`, deceleration `16 m/s²`, stationary threshold `0.1 m/s`, pivot turn `45°/s`, moving turn `18°/s`, and full-moving-steer speed multiplier `0.8`.

At actual near-zero longitudinal speed with no W/S request, A/D use equal/opposite commands for a centre pivot. While translating or coasting above `0.1 m/s`, A/D use gentle tracked correction: the outside side retains the travel-direction command while the inside side reduces toward zero and never reverses. Full forward D is left `+1`, right `0`; full forward A is left `0`, right `+1`. Full reverse D is left `0`, right `-1`; full reverse A is left `-1`, right `0`. The lower moving yaw rate and 80% full-steer speed prevent car-like turning without imposing textbook half-speed differential-drive behavior.

`LeftTrackCommand` and `RightTrackCommand` are read-only runtime values in `[-1, +1]` on both Player and Enemy. Positive means the future foot rollers should animate forward, negative means backward, and zero means stopped. No roller transforms or animation are assumed yet.

Mouse delta affects only the isolated cockpit hierarchy `cockpit/LookYaw/LookPitch/CockpitCamera`. Yaw is clamped to `±130°`, allowing the pilot to view the forward monitor, left radar wall, and right wall; pitch is clamped to `±70°`. Mouse look never rotates Player, `ExteriorCameraMount`, or `FrontFeedCamera`. `FrontFeedCamera` remains a fixed-local-orientation child of Player and therefore follows hull turns naturally. Escape releases the cursor, left click recaptures it, and cockpit look pauses while the cursor is unlocked. There is no jump, sprint, crouch, mouse steering, exterior-camera aiming, or Rigidbody locomotion.

### Player operating modes and shared cannon

`MechFirstPersonController` starts in `Travel` and uses explicit `Travel`, `TransitioningToFire`, `Fire`, and `TransitioningToTravel` states. T starts a code-timed transition with a serialized `2 s` code default and a current scene value of `6 s`. Both transitions brake through the existing movement path and reject locomotion, aiming, and fire; entering Fire clears residual speed. Elevation ownership is state-specific: the Animator alone owns the elevation pivot in Travel and `TransitioningToFire`, and Player procedural elevation is enabled only after deployment completes. Fire entry resets elevation to the authored straight-up pose (`90°`) with zero procedural offset, so every deployment forgets the prior firing session. Starting `TransitioningToTravel` stops aim input and sets `cannon = false`, while the remaining Fire elevation offset linearly returns to zero over exactly the same mode-transition duration on top of the Animator's folding base pose. At Travel completion the procedural offset is fully suppressed. Heading independently follows the shortest route to logical `0°` over that exact duration; generic aim sharpness and Animator clip speed control neither reset. Cockpit mouse look remains active in every state. In Fire, W/S step elevation and A/D step heading while hull movement receives zero input. New presses step `1°`; Left Alt selects `0.1°`; held input retains the existing delayed repeat. W is hard-clamped at vertical and S lowers through the forward firing hemisphere toward the configured non-negative minimum. Left click fires only in fully entered Fire with a locked cursor, and a cursor-recapture click remains suppressed. A successful shot starts an independent `5 s` default post-fire vulnerability timer. While it is active, the Player remains deployed and stationary in Fire, cannot fire again, and T cannot begin the Travel transition; cockpit look and cannon aim remain active. Rejected shots never start or reset the timer, expiry does not automatically fold the cannon, and T works normally afterward. The explicitly assigned Player Animator receives exact bool `cannon`: false in Travel/TransitioningToTravel and true in TransitioningToFire/Fire. Gameplay timing never depends on Animator clip data.

`Assets/Scripts/Combat/KartikarisCannonWeapon.cs` is a reusable input-agnostic articulation/fire API. It requires explicit heading pivot, elevation pivot, and fire point and independently exposes X/Y/Z local axes. Logical heading remains continuous and unbounded. Player-facing elevation is `0°..90°` by default: `90°` is the Animator-authored deployed vertical neutral and maps to a `0°` procedural offset; lower physical elevations map to positive selected-axis offsets, reaching `+90°` at horizontal for the current rig direction. The maximum is fixed at vertical and the configurable minimum is sanitized to the non-negative range. Normal Fire aim retains frame-rate-independent exponential smoothing. In Travel and deployment, the weapon only observes the Animator-written elevation pose and never writes the pivot. In Fire, prior-result detection composes the selected-axis offset over the deployed Animator base without accumulation. During folding, that offset linearly fades from the last visual aim to zero over `modeTransitionDuration`, continuously composing over the Animator's changing base; Travel then suppresses it completely. Heading remains applied before elevation so a descendant elevation pivot/fire point inherits it. The final physical muzzle measurement uses `asin(dot(firePoint.forward, referenceUp))`, clamps Player-facing output to `0°..90°`, and drives only the HUD runtime override; it is never fed back into articulation. Existing shell direction, projectile, cooldown, sound, muzzle/smoke/impact VFX, explosion, damage, and tree paths are preserved. Muzzle velocity has a `300 m/s` code default but the preserved scene value is `100 m/s`; cooldown is `5 s`. Cooldown remains weapon-owned and controls shell availability, while the separate controller-owned post-fire timer controls mobility/state commitment.

Each slot stores an optional definition, editable four-character display code, and physical index `1..6`; Previous/Next skip null entries and wrap. Selection events report previous/new physical indices plus direction. The Player scene order is `1: Super Explosive/SPEX`, `2: unassigned/ABST`, `3: unassigned/HOMG`, `4: unassigned/GUID`, `5: unassigned/----`, and `6: unassigned/----`; the project currently contains only the slot-1 definition asset. Weapon and predictor continue querying `SelectedShell`, so changes are immediately authoritative, while each projectile retains its launch-time definition reference. Enemy runtime selection remains disabled and its fixed definition remains independent.

Definitions select a projectile prefab or reuse the weapon fallback, optionally override the weapon's `300 m/s` base muzzle velocity, expose a per-shell ballistic travel-speed multiplier with a `1x` default, and contain type-specific gameplay plus future VFX/audio references. For multiplier `k`, the shared projectile launches at base velocity `× k` and applies per-projectile gravity `Physics.gravity × k²`, preserving the same world-space parabola while reducing real flight time to approximately `1/k`. Rigidbody automatic gravity is disabled runtime-only; global gravity is never modified. Continuous Dynamic collision, owner-ignore, impact handling, velocity-facing orientation, Standard HE, Airburst, Homing, and Guided Missile behavior remain shared and unchanged.

### Cockpit Artillery Computer

The right-side controls use one reusable gaze/interactable path. `shell prev`, `shell next`, `charge less`, and `charge more` have trigger `BoxCollider`s on layer 8, explicit action components, explicit matching Armature bone references, and a white inverted-hull URP outline. The outline creates one renderer-only proxy on demand, shares a Kartikaris-owned material, uses a property block, and creates no per-frame material instances. Button interactions expose a successful-press event and optional Animator trigger but currently move no bone.

Player charge selection is gameplay state on `KartikarisShellLoadout`, clamped to `0..3` and initialized to `1`. The visible `charge.1`–`charge.3` renderers are enabled bottom-to-top through `Renderer.enabled`. Values `1..3` preserve existing muzzle velocity through an explicit future scaling seam. A zero-charge fire attempt is rejected at the start of `KartikarisCannonWeapon.TryFire`, before cooldown, projectile, VFX, sound, or post-fire state; every attempt raises one warning hook and no warning presentation is implemented.

`ArtilleryComputerMonitor` is presentation-only 3D TextMeshPro, positioned slightly camera-side of the imported right-panel `monitor` material submesh. It uses proportional `LiberationSans SDF` because no monospace TMP asset exists, disables rich text, and keeps the font assignable. Reliable fallback glyphs are `#` for filled and `.` for empty mode cells; charge empties use three spaces. It shows `SHEL`, `CHRG`, predictor-derived horizontal `DIST`, predictor real-time `FLGT` as seconds/milliseconds, and a ten-cell mode bar from `MechFirstPersonController.OperatingModeProgress01`. Zero charge and Homing/Guided/no-solution predictions show unavailable distance/flight values. The view refreshes at 20 Hz or immediately when selection/charge dirties it and writes TMP only when content changes.

The Artillery Computer exposes button-press, shell-selection, charge-change, valid-shot, and zero-charge-rejection hooks. Explicit `ramrod`, `charges`, `coverpanel`, `revolver`, and `shell.1`–`shell.6` bone references are wired. The synchronized cover/ramrod/charge/shell/revolver loading and revolver-indexing animation sequence is intentionally deferred; no current interaction writes those transforms.

`KartikarisExplosion` retains unique multi-collider radial resolution and adds a forward-cone variant using half of the configured full angle internally. `KartikarisCombatAffiliation` provides the small Neutral/Player/Friendly/Hostile relationship used by homing and direct hits without name checks. `KartikarisMechHealth` now has a `1000 HP` code default; existing serialized scene values require manual confirmation. `KartikarisBallisticSolver.TrySolveTrajectory` independently provides low/high gravity solutions, vertical-offset handling, reachability failure, launch direction, and flight time. It solves direction from base velocity/gravity so the spatial aim is unchanged, then reports real-time flight duration as base time divided by the selected multiplier.

### Runtime tree interaction

`Assets/Scripts/WorldInteraction/KartikarisTreeInteractionRuntime.cs` uses a runtime TerrainData clone, stable Terrain tree indices, and a local spatial hash. Each prototype has editable trunk radius, height, and vertical offset metadata. Six profiles are initialized from suitable source `CapsuleCollider` dimensions; the four mesh-only prototypes use conservative named defaults rather than leaf/renderer bounds. No standing-tree GameObjects or Collider components are created.

`MechTreeCrusher` performs a horizontal swept-circle versus virtual-trunk test before `CharacterController.Move`, with CharacterController/trunk height overlap. The earliest impact clamps movement to just before the trunk, so the controller cannot slide tangentially around it. The struck tree is made inactive and hidden immediately, and the controller zeros longitudinal speed. Held W/S can accelerate normally on the next frame.

`FallingTreeVisual` starts the copied tree upright, disables every copied Collider, removes Rigidbody behavior, and eases over `0.7 s` toward the impact direction projected onto the Terrain tangent. It then remains as non-blocking session trail evidence. Synthesized break and ground-impact placeholders play at fall start/completion.

Explosion tree effects reuse a bounded `CrushTreesInRadius` query over the existing spatial cells. Only active indices inside the configured horizontal radius are hidden once, and the existing non-physical fall path sends their visuals away from the blast before the normal crack/thud behavior. Gameplay queries update virtual state, Terrain tree scale, falling visuals, and returned crush counts synchronously, but only request a Terrain refresh. `KartikarisTreeInteractionRuntime.LateUpdate` batches those requests into one `Terrain.Flush()` after physics callbacks, avoiding Terrain-managed immediate destruction during projectile contacts. Initialization and shutdown retain direct flushes outside gameplay callbacks. No explosion scans the full 25,000-tree array.

### Enemy artillery and relocation prototype

`EnemyTest` chooses its initial Terrain-grounded position uniformly from valid Terrain points whose horizontal Player distance is between `300 m` and `1000 m`. It rejects an invalid search instead of silently placing inside the minimum distance. Later relocation destinations are also rejected unless they remain inside that same Player-distance band, while individual moves retain the `100 m` cap. Preparing targets the Player's current position, requests the preferred high/low solution from `KartikarisBallisticSolver`, rejects unreachable/out-of-elevation solutions, sets the shared weapon's logical heading/elevation, waits for the physical `firePoint.forward` to align, and calls `KartikarisCannonWeapon.TryFire()`. Successful shots therefore use the assigned Standard HE definition, real projectile, smoke/VFX, cooldown, and acoustic event. They also enter an explicit deployed, stationary `PostFireVulnerability` state for `5 s` by default; only after that independent timer expires does Enemy choose a relocation, fold through its normal transition, and move. Failed solutions or shots bypass the commitment timer and fold/relocate rather than deadlocking. No target lead, uncertainty, terrain obstruction optimization, or Guided Missile Enemy use exists.

Subsequent relocation is not direct Transform sliding. For large heading errors at near-zero speed, Enemy uses the shared equal/opposite stationary pivot. Once aligned within `15°`, it accelerates forward and uses proportional, gentler moving tracked correction for residual error. It reads Player's pivot/moving speeds, threshold, moving-steer multiplier, translation tuning, and gravity live. It moves only along its own forward direction through a matching CharacterController. Its matching `MechTreeCrusher` uses the same runtime tree index and crush radius, so it stops/crushes/reaccelerates through trunks via the same movement path as Player. Enemy does not reverse or strafe while autonomously navigating, and no NavMesh/pathfinding or new leg-animation parameter was introduced.

### Prototype audio and sound propagation

`Assets/Scripts/Audio/PrototypeAudioSynthesis.cs` adapts the compact deterministic `AudioClip.Create`/`SetData` approach inspected in Closing IN's `ArtilleryAudio.cs`. It creates one cannon boom, subtle radar beep, tree crack, and tree thud per sound-service lifetime; there is no per-frame clip allocation or imported audio asset.

`KartikarisSoundPropagation` assigns every cannon/decoy-compatible acoustic emission a stable event ID and internal emission/source record, records the emitter's `KartikarisAffiliation`, then schedules the Player and each accepting registered `KartikarisAcousticReceiver` independently at the default `343 m/s`. Sound Probe receivers use relationship-based hostile-only filtering: Player/Friendly owners reject Player/Friendly events and accept Hostile events, while Hostile owners naturally do the inverse. Neutral acceptance remains separately configurable. Unregistering a receiver also cancels its pending deliveries, preventing destroyed probes from receiving later arrivals. Detection reports contain event ID, emitter affiliation, stable receiver identity/kind, arrival time, sound speed, and receiver position, but no authoritative source position. The cockpit Player delivery and boom/beep/sound-origin presentation have an independent enable and are not silenced by probe filters.

### Dedicated cockpit radar

`Assets/Scripts/Radar/RadarContact.cs` is the reusable contact declaration. It records a position source, friendly/enemy affiliation, future-facing category metadata, manual/debug spotted state, and active state. Enabled contacts register themselves without requiring a per-scene list. Active friendly contacts are eligible regardless of spotted state; active enemy contacts require either the preserved manual flag or at least one source ID. `AddSpotSource`/`RemoveSpotSource` let multiple drones or future spotters contribute independently, so one source ending cannot clear another source or a manual spot.

`Assets/Scripts/Radar/KartikarisRadarController.cs` owns the radar presentation. It keeps the player marker centred and maps world `+Z` to up and world `+X` to right, independent of player yaw. Runtime range initializes from the configurable `3000 m` default and clamps to the serialized `250–3000 m` bounds. New Input System mouse-wheel input changes only `currentRadarRange`: wheel up zooms in, wheel down zooms out, and the `0.002` exponential sensitivity gives proportional rather than fixed-metre steps. The physical Canvas, radar mask/background, centre marker, sweep, and marker dimensions never scale. The controller remains the shared world-XZ-to-radar-local conversion for contacts, probes represented as contacts, drone-spotted targets, artillery assistance, TDOA, and future positional overlays. Eligible in-range contacts receive runtime Image views under `Contacts`; friendlies are blue and enemies are red. The clockwise sweep uses the donor's `0.8` rotations-per-second timing, brightens a contact when it crosses that contact's bearing, and fades the ping over `0.5 s`. World-position views outside `currentRadarRange` are hidden rather than clamped to the edge and reappear when range expands. ### Player ballistic radar assist

`KartikarisFireControlPredictor` reads the Player weapon's current `firePoint`, currently selected shell, effective base muzzle velocity, ballistic multiplier, gravity behavior, Terrain, and configurable collision layers. Before sampling, it explicitly applies the weapon's final post-Animator procedural pose through the same method used immediately before real firing; this prevents script execution order from exposing the Animator-restored vertical elevation while heading still appears current. For assist presentation, bearing comes from the assigned heading pivot/compass torso forward projected onto the Player plane. The muzzle contributes only signed elevation relative to Player up, clamped to `0°..90°`, and the predictor reconstructs a torso-forward launch direction. Temporary backward/downward authored transition poses therefore cannot send the always-visible assist behind the torso or below horizontal. This clamping is assist-only; actual shells still launch along physical `firePoint.forward`. The predictor evaluates the constant-gravity parabola in base ballistic time and sweeps every consecutive segment with a non-alloc ray/sphere cast, filters the owning Player hierarchy, and selects the nearest valid world hit. Because the spatial equation intentionally omits time multiplier `k` while reported real flight time divides by `k`, `1x/2x/3x` produce the same predicted point. Standard HE reports the first impact. Airburst reproduces the configured arming margin and descending ground-clearance crossing and reports the expected configured detonation height. Homing and Guided Missile return no static prediction.

`KartikarisArtilleryAssistController` adapts the read-only FireForEffect/Closing IN `AimingAssistController`: a full-radar heading image rotates clockwise from the predictor's explicit compass/torso-forward bearing and its child elevation image slides radially to the predicted point through the radar controller's common current-range mapping. It is Player-only and shows valid in-range Standard HE/Airburst assistance in every operating state by default; the serialized `requireFireMode` option can restore Fire-only presentation. Out-of-range predictions hide instead of clamping to the edge; invalid trajectories and Homing/Guided remain hidden. It polls live aim/configuration, creates no UI hierarchy, and creates no endpoint dot/contact. On a successful Player `Fired` event, it captures that shot's predicted flight time, tracks the returned projectile, and drives the optional `ImpactEstimate` TMP label as `Impact: 5.53s`. The countdown uses game time, clamps visually at `0.00s` if prediction and physics differ, and hides when the launched projectile is destroyed by impact or lifetime. A direct `RadarRoot/ImpactEstimate` child resolves automatically; an explicitly assigned TMP reference remains supported. Failed shots never start it. The already imported `heading assist.png` and `elevation assist.png` match the donor PNG hashes and GUIDs and were not modified.

### Heading compass and elevation tape

`Assets/Scripts/UI/KartikarisHeadingElevationHUD.cs` drives the existing VisionHUD elements every `LateUpdate`. Heading samples only `Player.eulerAngles.y`: world `+Z` is `000.0°`, `+X` is `090.0°`, `-Z` is `180.0°`, and `-X` is `270.0°`. The value is normalized to `[0, 360)`, while a `Mathf.DeltaAngle`-accumulated internal heading keeps the 359.9/0 boundary continuous. Increasing hull heading moves the heading tape left; decreasing heading moves it right. Cockpit head look, cameras, movement state, and firing state do not gate or influence it.

Elevation accepts the cannon weapon's runtime physical muzzle measurement when that integration is assigned; otherwise its existing manual/transform fallback remains available. `SetElevationDegrees(float)` and every display path clamp to `0°..90°`; three component context commands set `0`, `45`, and `90` degrees while manual mode is active. Increasing elevation moves the vertical tape down and values outside the finite range are hidden.

Both tapes use the existing notch objects as templates. Every notch interval is exactly `10°`. Code exposes independent `headingNotchSpacingPixels` and `elevationNotchSpacingPixels` fields with `40 px` defaults; the current scene externally serializes both as `30 px`. Movement scale is derived as `spacing / 10°`, so the current scene produces `3 px/degree`: each ten-degree change advances one 30 px interval, a full heading circle spans 36 intervals/1,080 px, and the finite `0°..90°` elevation range spans nine intervals/270 px. Changing visual spacing cannot change the semantic ten-degree resolution. Pool counts derive from each masked RectTransform extent plus a four-notch buffer on both sides. The fractional angle moves a pooled root; notch GameObjects are not instantiated, destroyed, or rebuilt per frame. Text remains independently formatted to one decimal place as `000.0°` for heading and unsigned elevation values such as `0.0°`, `45.2°`, and `90.0°`; negative zero is normalized away.

## Important Architecture Decisions

- Use built-in Unity Terrain/TerrainData rather than Ritual Division terrain chunks.
- Preserve the fresh Unity 6000.3 package, URP, ProjectSettings, and third-party import baselines.
- Keep terrain and forest generation deterministic with independent local random streams.
- Keep standing trees as Terrain tree instances and avoid a GameObject/collider/Rigidbody per tree.
- Defer and batch gameplay `Terrain.Flush()` calls until `LateUpdate`; collision/explosion callbacks may update virtual tree state immediately but must not force Terrain-managed object rebuilds during physics contacts.
- Keep TerrainCollider tree collisions disabled; use editable per-prototype virtual trunks in the existing spatial hash.
- Resolve virtual trunk impacts before `CharacterController.Move`, clamp to the earliest hit, deactivate the tree immediately, and zero only longitudinal momentum rather than adding a stun.
- Use `CharacterController` plus the new Input System for the first-person mech.
- Treat W/S as signed longitudinal throttle and A/D as tracked steering: equal/opposite stationary pivot commands below the actual-speed threshold, gentler inside-side reduction while moving, and no camera-derived movement.
- Keep the shared tracked-drive abstraction pure and small; CharacterController translation/yaw remains deliberately kinematic rather than a differential-drive physics simulation.
- Keep pilot head yaw/pitch on the isolated cockpit stage so looking around never changes hull or exterior-feed orientation.
- Isolate the physical cockpit presentation space with URP Rendering Layers: exterior lighting stays on Default, cockpit meshes stay on Cockpit, and cockpit-local lights opt into Cockpit without blocker geometry or Unlit materials.
- Keep Player operating-mode/input policy in `MechFirstPersonController`, reusable articulation/cooldown/spawning in `KartikarisCannonWeapon`, and reusable ballistic behavior in `KartikarisArtilleryProjectile`.
- Keep post-fire mobility commitment controller-owned and success-gated: Player and Enemy start the same semantic timer only after `TryFire()` returns true; weapon cooldown remains independent.
- Layer weapon articulation after Animator evaluation using the current animated local pose plus one logical selected-axis quaternion; remember the previous procedural result so static pivots cannot accumulate drift. Never search imported transform names or increment Euler angles.
- Keep cannon heading unbounded for continuous rotation, smooth only the visual weapon offsets toward discrete logical aim targets with one frame-rate-independent lerp update per frame, and use logical heading `0°` as the smoothly approached Player-forward target when leaving Fire.
- Let the Animator exclusively own elevation in Travel and deployment. In Fire, treat its authored deployed vertical pose as physical `90°` and layer a non-accumulating selected-axis offset in `[0°, 90°]` for the current rig direction. During folding, linearly fade that offset to zero over the mode-transition duration while retaining the Animator's changing base, then return full ownership to the Animator. Calculate displayed HUD elevation independently from final `firePoint.forward` relative to the Player/reference local XZ plane.
- Preserve fixed startup locking for Enemy while allowing the Player's six physical slots to select available definitions at runtime; keep all shell behaviors on the shared Rigidbody projectile path rather than duplicating projectile implementations.
- Keep ballistic traversal scaling per shell. Solve the spatial arc from base velocity/gravity, then launch each projectile at velocity `× k` with private gravity `× k²`; never change global gravity or acoustic time.
- Predict Player impact from that same base spatial parabola, sweep between samples, and divide only the diagnostic flight time by `k`; never instantiate a projectile for fire-control presentation or let Homing/Guided advertise a false static landing point.
- Keep the assist bearing tied to the same assigned torso/heading Transform as the compass. Clamp assist-only elevation to the torso-forward `0°..90°` firing hemisphere so transition animation poses cannot advertise backward or downward solutions; do not change the real shell's physical launch direction.
- Start the radar impact countdown only from the Player weapon's successful `Fired` event, capture one flight-time estimate for that projectile, and stop following aim changes afterward. Hide when that projectile is destroyed; never start/reset it for a rejected shot.
- Keep low/high no-drag trajectory mathematics in `KartikarisBallisticSolver`; Enemy requests a solution and its `baseTime / k` diagnostic, physically aligns the shared weapon, and fires only through `TryFire()`.
- Use small explicit affiliation components for hostile homing/direct-hit decisions; never infer teams from object names.
- Correlate only receiver-accepted acoustic detections by stable event/receiver IDs and generate TDOA curves solely from historical receiver positions plus arrival-time differences; never feed authoritative source position into localization. Carry emitter affiliation on every cannon/decoy event and filter through affiliation relationships rather than Player name checks.
- Keep module loadouts fixed and top-row 1/2 input, but route presses through per-slot module actions so deployment, repeat activation, recall, and cooldown state stay with each behavior rather than a controller switch.
- Give every world module one owner-aware deployable lifecycle and destruction reason. EMP discovers only bounded collider overlaps and invokes that shared contract; disable/destroy cleanup must remove acoustic registrations, spot-source ownership, and module runtime references.
- Source Enemy locomotion tuning live from the Player controller and use the same CharacterController/tree-crusher path rather than duplicating faster Transform movement.
- Keep radar coordinates world-north-up and player-centred rather than rotating the map with the mech.
- Centralize every world-position overlay through the radar controller's `currentRadarRange` mapping. Mouse-wheel zoom changes only that view transform; never scale the radar hierarchy, marker sizes, gameplay objects, acoustic measurements, or historical receiver positions.
- Render the zoom-aware distance face as a UI mesh with exact `500 m` rings/subdivisions. Keep sweep and heading indicators as image overlays, generate no numeric distance text, and rebuild grid geometry only when range, size, or style changes.
- Keep contact eligibility in `RadarContact`, presentation/bearing error in `KartikarisRadarController`, and finite-speed delivery in `KartikarisSoundPropagation`.
- Keep radar spotting source-aware: manual/debug spotting is independent, and every drone adds/removes only its own source ID.
- Treat cannon hints as historical sound-source information and never as an automatic enemy spot.
- Reuse only the donor radar's general grid/sweep/ping/fade presentation; do not port its artillery, impact, projectile, uncertainty, or game-manager assumptions.
- Reuse the donor assist's nested rotate-parent/slide-child presentation with the already imported images, but replace its flat ideal-range formula with Kartikaris world collision prediction and create no endpoint dot.
- Keep the physical cockpit radar on layer 8 so only `CockpitCamera`, not `FrontFeedCamera`, renders it.
- Drive cockpit heading from the physical Player hull, not head look, either camera, movement input, or weapon state.
- Keep heading world-north based with a wrap-continuous scroll phase and keep Player-facing elevation finite at `0°..90°`.
- Pool only the visible `10°` notch strips plus a small buffer, preserving the existing notch graphics and avoiding per-frame hierarchy churn.
- Preserve the HUD's manual/API fallback, while allowing the assigned cannon weapon to supply the final physical muzzle elevation at runtime.

## Known Issues / Limitations

- The ten Synty tree prefabs are ordinary mesh prefabs rather than SpeedTree assets. Unity may warn that their shaders are not `Nature/Soft Occlusion`; their working URP materials are intentionally unchanged.
- Terrain tree billboard transitions, lighting quality, tank-control feel, cursor behavior, cockpit look sensitivity, and sustained performance require interactive Editor/Play Mode inspection on the intended hardware.
- The `Warning Light` red Point Light remains inactive in the saved scene, matching its pre-task state; enable it manually or through intended gameplay logic when verifying Cockpit-only illumination.
- The current 25,000-tree batch result is a correctness/generation-time check, not an FPS benchmark.
- Virtual trunk sizes are prototype defaults, not final art-authored collision measurements; the four mesh-only trees use conservative named fallback values and require an interactive feel pass.
- Fallen trees are non-physical visuals and never block the Player. Their copied source colliders are disabled and no Rigidbody simulation is used.
- Enemy relocation uses player-style forward-only tank locomotion and crushes blocking trees, but its artillery has perfect current-position knowledge and no target lead, uncertainty, obstruction analysis, NavMesh, route planning, avoidance steering, reverse recovery, or new leg-animation parameter.
- Roller transforms do not exist in the current model hookup, so left/right tracked commands are exposed but not yet animated.
- Pivot/moving yaw speeds, the `0.1 m/s` mode threshold, and the `0.8` full-steer speed multiplier need an interactive feel pass on the redesigned roller-foot model.
- Enemy initial placement can overlap a virtual/visual tree; startup concealment placement was intentionally kept simple. The current square Terrain bounds limit the actually reachable portion of the configured `300–1000 m` band, and a failed bounded search leaves Enemy unmoved rather than violating the minimum distance.
- Sound delay uses Player distance at emission time. There is no moving-receiver interception, acoustic occlusion, forest attenuation, echo, or propagation around terrain.
- The synthesized cannon/tree/beep clips are functional placeholders and require subjective loudness/timbre tuning in the cockpit.
- Tracking Drone is the only gameplay spot source currently implemented; cannon sound hints deliberately do not reveal exact contacts.
- The current rig is expected to lower forward when the selected elevation axis receives a positive procedural offset. The reported torso/`cannon.1` assignments, final direction, and transition-boundary visual result have not been independently Play Mode verified.
- Heading/elevation tape pixel density and text placement still require a subjective cockpit readability pass at the intended display resolution.
- Very small notch-spacing values increase the visible pool size; use practical spacing values rather than compensating with extremely dense pools.
- The left radar wall is not in the straight-ahead cockpit view; move the mouse left to turn the pilot's head toward it.
- Only `Super Explosive` currently exists as a shell-definition asset, so Player slot 1 is the only available slot until real Airburst/Homing/Guided definitions are created and assigned. Slots 2–6 safely remain null.
- The Artillery Computer monitor currently uses proportional `LiberationSans SDF`; assign a project-owned monospace TMP font for final alignment. Its material-submesh placement and 10 m staged interaction reach are wired, but text readability, gaze feel, and outline thickness require an interactive cockpit pass.
- Full coverpanel/ramrod/charges/shell/revolver loading animation, button-bone motion, and revolver indexing are intentionally deferred; only explicit references and events exist.
- The procedural grid is code-complete but intentionally not wired into the saved scene. The current static `RadarBackground` PNG combines cardinal headings with obsolete numeric distance guides, so a labels-only image overlay must be supplied manually when that composite is disabled.
- Shell definitions, Enemy ballistic aiming, acoustic modules, and a Player landing-assist firing computer now exist, but there is no loadout UI, ammunition count, drawn trajectory arc, impact dot, armor, blast occlusion, fragmentation, death presentation, moving-target lead, drag/wind, missile monitor wiring, module retrieval, POI generation, streaming, or save persistence.
- Ballistic multipliers above `1x` are intended first for Standard HE and Airburst. Homing/Guided still use real-time turn-rate values, so their spatial steering authority changes when flight time is compressed; leave those definitions at `1x` until separately tuned.
- The `1x–3x` ballistic equivalence and predictive Airburst crossing are mathematically/static validated but not yet Play Mode tested against PhysX integration and Terrain CCD.
- The yellow assist and both existing Sound Probe slots are now wired in the saved scene. Sound Decoy/EMP/Tracking Drone actions, definitions/prefabs, deployable layers, VFX, and drone Terrain/target references remain unwired. The predictor currently uses `Everything` and a `0.05 m` sweep despite the real shell using impact-mask bits `1112` and a `0.0025 m` capsule radius; this scene tuning should be matched before trajectory acceptance testing.
- Predictor sampling is a configurable no-drag constant-gravity approximation of the Rigidbody path. It ignores virtual Terrain trees by design and still needs controlled 1x/2x/3x Standard and Airburst comparison shots against PhysX/Terrain.
- Tracking Drone uses direct transform flight with bounded overlap detection, not obstacle avoidance or a flight physics model. The `100 m` detection range and `-20 m` default follow offset are provisional, and forest clearance/detection geometry require Play Mode tuning.
- Only Player-side module input is implemented. Enemy module deployment/decision-making, drone retrieval inventory, deployable models, and final VFX/audio assets remain out of scope.
- Weapon setup remains manually owned. Player/Enemy health components, all three VFX prefab slots, tree-runtime reference, selected pivot axes, fire point, sound/HUD integration, and shell prefab Rigidbody/Collider/projectile configuration must be confirmed before acceptance.
- Normal `Aim Lerp Sharpness = 12` remains an untested code default. The Travel reset uses its own exact-duration linear interpolation for both heading and elevation; its composition with the authored fold still requires a Play Mode animation check.
- `KartikarisMechHealth` only records death and raises events; it does not disable controllers, Enemy AI, visuals, or root GameObjects.
- Explosion damage uses the health component's Transform position and does not model hull bounds, line-of-sight, terrain shielding, armor, or teams. The stored team ID is future-facing and currently applies no filtering.
- Converted JMO WarFX effects preserve their authored material modes through one URP compatibility shader, but exact additive intensity, smoke multiplication, soft-particle intersections, lit decals, and scrolling appearance require a visual comparison in Game View. Soft particles require the active URP renderer/camera to provide a depth texture.
- The original JMO legacy shader source files remain in the imported package for provenance but are unreferenced by the 130 audited materials; newly imported vendor materials can be upgraded through the Kartikaris VFX menu command.
- HUD muzzle elevation assumes `firePoint.forward` is the true barrel direction. Incorrect fire-point orientation produces an incorrect display but no longer changes articulation.
